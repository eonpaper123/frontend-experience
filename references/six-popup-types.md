# Six Popup Types: Select by Task

Use this reference when a request says "add a popup" or names a Modal, Drawer, Toast, Dropdown, Popover, or Tooltip. First identify the user's task, whether background interaction must stop, whether the surface contains controls, and what closing commits or cancels. These names describe different aspects of an interface rather than six mutually exclusive HTML roles: a drawer can be a modal dialog, and a dropdown can use the Popover API.

## Selection and semantics

| Type | Task and interruption | Implementation contract |
| --- | --- | --- |
| Modal | A bounded task or decision that requires attention before returning to the background. Use interruption only when the task warrants it. | Name the dialog, move focus inside, make the background inert, contain keyboard focus, and return focus to the invoker or the next logical target. On the web, prefer the existing accessible dialog component or `<dialog>.showModal()`; a custom modal needs `role="dialog"` and `aria-modal="true"` plus actual modal behavior. A center position or dark backdrop alone does not create modality. See the [APG modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) and [MDN dialog reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog). |
| Drawer | Details, filters, or editing alongside existing context; choose modality separately from side or bottom placement. | A modal drawer follows the modal contract. A non-modal drawer keeps the background operable, provides a keyboard route between contexts, and must not trap users or claim `aria-modal="true"`. Use dialog semantics only if it is a dialog; navigation may remain a `nav` region. `<dialog>.show()` is a native non-modal dialog option. See the [MDN dialog reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog). |
| Toast | Nonblocking feedback about a real action or state, without moving focus. | Routine feedback can use `role="status"`, which is implicitly polite; reserve assertive `alert` for urgent information. Do not impose a universal three-second timer: essential errors, required decisions, and time-sensitive actions need persistent or recoverable information and enough time to act. Use inline or persistent feedback when transience would lose the information. See [MDN status](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/status_role) and the [APG alert pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/). |
| Dropdown | An anchored set of commands, navigation links, or selectable values; identify which one before implementing. | Commands use the menu-button/menu pattern and its keyboard model; ordinary navigation can remain a disclosure containing links. Value selection should use native `select` when sufficient, or the appropriate listbox or combobox pattern. Editable suggestions need combobox input semantics. Do not assign `menu` to every visually dropped list or copy menu key handling into a form field. See the APG patterns for [menu button](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/), [listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/), and [combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/). |
| Popover | Anchored contextual information or a small interactive task without blocking the whole page. | Choose semantics from the contents: an interactive dialog, menu, or plain information region as appropriate. HTML `popover` supplies display and top-layer behavior, not those content roles or a focus trap. Popover API surfaces are non-modal; `popover="auto"` supports light dismissal, while `manual` requires explicit controls. An arrow is optional visual treatment, not a semantic requirement. See the [MDN Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API) and [popover attribute](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/popover). |
| Tooltip | Short supplemental description on hover or keyboard focus, with focus staying on the trigger. | Use `role="tooltip"` and connect the trigger with `aria-describedby`; retain an accessible name for the control. Include no focusable controls. Support Escape dismissal and pointer movement onto the tooltip without premature disappearance; keep it visible while hover or focus still requires it. Essential instructions need an accessible persistent or touch path. If users must interact inside it, select another pattern. See the [APG tooltip pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/) and [WCAG guidance for hover or focus content](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html). |

## Opening, closing, and feedback

- Describe the contract as **task -> type and modality -> content and actions -> close or cancel outcome -> feedback**. Example: "Edit details in a non-modal drawer; preserve the draft when closing, save only on Save, announce the verified save result without moving focus, and keep errors beside the affected fields." A destructive confirmation, when warranted, states the actual consequence and offers a clear safe exit.
- Follow the selected pattern's keyboard contract. Escape normally dismisses a modal dialog, menu, combobox popup, or tooltip as their platform pattern specifies. Define outside-click and swipe behavior separately. Closing must not silently submit or discard unsaved work; preserve the draft or route the close request through the product's explicit discard decision. For native dialogs, handle the `cancel` event when a close request needs that guard. Do not assume a backdrop means clicking it closes the surface.
- Fit width, placement, scrolling, safe areas, and motion to content and the real viewport. Example values such as a 420px drawer, a three-second toast, a tooltip delay, or a red confirmation button are not shared defaults. Red expresses a destructive action where the design system uses it; a modal is not inherently destructive.
- Reuse the existing [stateful-motion contract](../SKILL.md#preserve-continuity-in-stateful-motion) and [component motion tokens](component-motion-tokens.md) for anchored entry and return, interruption, and reduced motion. Use platform-native accessibility APIs for native apps and Mini Programs; web ARIA attributes are not portable implementations.

## Observable acceptance

On the changed target surface, exercise open, keyboard and touch operation, explicit close, Escape and outside click where supported, and reopen with draft or selection state intact as specified. Confirm accessible name and role, initial and restored focus, background operability matching modality, actual command versus selection behavior, readable and recoverable feedback, and tooltip hover and focus dismissal. Check viewport edges, scroll and soft-keyboard behavior where relevant, interruption, and reduced motion using the skill's existing verification gate. Documentation alone is not runtime acceptance.

## Provenance and limits

The selection vocabulary was inspired by Mason's public article on [six popup types](https://www.xiaohongshu.com/discovery/item/6ad9c8e7000000000d009bb1). The implementation contracts are independently written and grounded in the linked WAI-ARIA Authoring Practices, MDN, and WCAG guidance. This repository includes no source media, third-party component code, or assets. The reference is guidance, not a component kit, dependency, rendered demonstration, accessibility certification, or set of universal dimensions and timings.
