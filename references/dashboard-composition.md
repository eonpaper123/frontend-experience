# Dashboard decision hierarchy and composition anchors

Use this when designing or reviewing a dashboard, analytics workspace, operations console, or data-heavy admin surface. It distills observed composition examples into decision prompts and comparison anchors; it is not a design system, a chart specification, or evidence that any example works for a different product.

The percentages below are annotations recorded from a dashboard-composition demonstration, not independently measured values. Several rows are intentionally incomplete and need not sum to 100%. The `structure` percentages use an unstated or varying denominator; do not reinterpret them all as main-column width. Frame labels such as `L7/L12/L18/L30` are names in the example, not verified contrast ratios, luminance values, or design tokens. No source screenshots or assets are included here.

## Make the dashboard answer a decision

1. **Start from the decision and data contract.** Name the primary users, decisions, actions, entities, time windows, units, comparison baselines, freshness, uncertainty, permissions, and error/empty/loading states. Choose overview, alert queue, investigation, or action flow from that contract; do not begin by selecting one of the visual styles below.
2. **Ask three composition questions.** Where does the heaviest visual mass land? Who or what receives the first screen? What can be removed? Visual weight includes occupied area, contrast, imagery, type scale, and persistent chrome—not color alone. Give the first screen to the user's most important decision, urgent state, or recurring task, not automatically to headline KPIs. Remove duplicate framing, labels, controls, and decoration, never units, provenance, thresholds, or state meaning.
3. **Assign color by role.** Define neutral surfaces, text, series, categorical state, severity, selection, and action colors before tuning percentages. Multiple chart series and green/yellow/red state sets may legitimately need several distinguishable colors; preserve direct labels or a clear legend and a non-color cue. “At most four colors,” “one accent per style,” and “one heavy color per page” are not universal rules.
4. **Earn density through hierarchy, not one shell token.** Use grouping, alignment, spacing, type hierarchy, stable scales, comparison order, filters, and progressive disclosure to make a dense view scan. Consistent geometry can help, but density is not solved by applying the same radius everywhere; `22` is one filmed example, not a default.
5. **Let state and action outrank decoration.** Alerts, failures, freshness, live/paused state, threshold breaches, confidence, and their action paths must remain legible before glass, photography, large display type, or a dramatic dark field. A large title can coexist with separators when the information architecture needs them; “no horizontal line” and “large title” are not mutually exclusive laws.
6. **Verify with representative data.** Test long labels, dense and sparse ranges, zero/negative/outlier values, multiple series, color-vision differences, keyboard/focus, zoom, responsive breakpoints, and role-specific first screens. Confirm that the visual hierarchy still matches task priority and that charts, alerts, and state remain understandable without decorative effects.

## Reuse an admin shell without inheriting a foreign product

[satnaing/shadcn-admin](https://github.com/satnaing/shadcn-admin) is a useful MIT-licensed reference for a React/Vite admin shell: responsive navigation, nested/collapsible sidebar, command search, data-table surfaces, theme and direction controls, authentication/error screens, settings, and common business-page shapes. Its own README calls it a dashboard UI collection rather than a starter project, and labels Clerk authentication as partial. Treat it as a source to inspect and selectively adapt, not as a production backend, an authentication system, or a reason to replace a working stack.

1. **Inventory the shell before copying it.** Map the target product's routes, roles, entities, actions, global navigation, search scope, table state, settings, authentication states, and 401/403/404/500/503 ownership. Reuse only the page or shell pieces that satisfy that map; a broad demo route list is not a requirements document.
2. **Keep architecture selection independent.** Vite plus TanStack Router/Query/Table is one coherent SPA example, not a rule that admin products never need SSR, server rendering, or another router. Preserve the current framework unless deployment, rendering, data, or navigation requirements justify a change. Add only dependencies the selected slice actually needs.
3. **Separate UI coverage from application completeness.** Demo forms, tables, search, charts, auth pages, and error pages prove interface coverage only. Connect authoritative APIs, validation, permissions, real business actions, loading/empty/error states, session expiry, and real navigation before calling the application usable.
4. **Preserve local component changes deliberately.** The upstream README identifies modified shadcn components and RTL-specific adaptations; a later CLI update can overwrite those differences. Diff the exact component, retain project tokens and accessibility behavior, and test both text directions when RTL is in scope rather than bulk-updating the component set.
5. **Accept the shell on real workflows.** Verify deep links, refresh/back behavior, keyboard command navigation, focus, collapsed and mobile navigation, wide tables, localization/RTL, role-restricted routes, auth expiry, and representative data. A polished dashboard screenshot or successful static build does not prove the connected internal tool works.

## Eight source patterns to compare, not copy

| Source pattern | Source readout and composition observation | Reusable question and boundary |
| --- | --- | --- |
| 1. Large color-block regions | Coral 18%, ice blue 13%, periwinkle 11%, sage 9%; source `structure 54%`; left side reads metrics and right side holds alerts/capacity/assistant actions. | Could bounded color regions make unlike work zones scannable? Keep data/state semantics in labels and structure; the source's “over four becomes a palette” is a warning about fragmentation, not a four-color limit. |
| 2. Image-card flow | Warm white 80%, ink 4%, UI color 2.3%; photos carry most chroma and the current state gets an orange cue; image precedes supporting text. | Use imagery as the primary content only when recognition of the item is part of the task. Protect text contrast and status meaning across unpredictable photos; one accent is this example's choice, not a dashboard rule. |
| 3. Glass layers | Gradient 64%, blue-violet layer 28%, solid fill 1%; source `structure 5%`; icon rail, primary metrics, and persistent transfer list form three zones. | Can translucency express depth without weakening labels, charts, or state? Test the real background and transparency conditions; a decorative gradient must not become the data scale or the only grouping cue. |
| 4. Dense card wall | Source `structure 100%`; navigation moves to the top, content uses full width, radius `22` repeats, and green/yellow/red remain available for state. | Does the user need parallel scan or sequential drill-down? Build order and grouping from comparison tasks, preserve state colors, and expose deeper levels intentionally; repeated radius and four-across cards alone do not create hierarchy. |
| 5. Fluorescent highlight | Near-white 80%, ink 12%, fluorescent lime 5.8%; source `structure 70%`; one primary vertical flow and a secondary jump area; pill geometry repeats. | Can a restrained highlight keep progress and the current mark visible? Do not suppress additional categorical, series, or severity colors when the data requires them, and do not force every control into a pill. |
| 6. Editorial composition | Near-white 50%, pale blue-gray 44%, saturated color 1.6%; source `structure 33%`; large display heading and few full-width separators. | Can scale, whitespace, and a restrained surface shift clarify entry and reading order? Preserve scanable chart structure and separators when needed; large type and horizontal rules are a compositional tradeoff, not a forbidden pairing. |
| 7. Dark top field | Cream 59%, one dark field 37%, color 1.3%; a persistent heavy header precedes three equal cards and a lower list. | Does a stable heavy field orient the user or consume space needed by the task? The source avoids a second heavy block, but additional visual weight is valid when alert priority, comparison, or navigation requires it. |
| 8. Dark console | Dark field 95%, color 1.4%, three gray roles 3%; source `structure 17%`; five indicators, a central multi-series chart, supporting panels, and source labels `L7/L12/L18/L30`. | Can restrained luminance layers preserve hierarchy while bright state/action colors stay salient? Treat the gray labels as unverified source names, then measure real text, border, focus, series, and alert contrast; never collapse required series or statuses into one accent merely for cleanliness. |

Select or combine only the relationships that serve the current data and decisions. Re-derive tokens and proportions from the actual design system, viewport, localization, accessibility targets, and representative dataset; do not average these examples into a ninth preset.
