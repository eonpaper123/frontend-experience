# Frontend Experience

Connect product intent to a working client experience. This is a shared workflow for substantial frontend work, not an aesthetic, component library, or mandatory research ceremony.

## Scale the work

- For a local styling fix, control change, or established-screen extension, inspect the surrounding design and implement the scoped change. Do not restart reference research or redesign the product.
- For a new experience, substantial visual redesign, new user journey, or a change of rendering model, establish direction and constraints before implementation.
- For analysis or review requests, inspect and report; a recommendation is not permission to implement it.

## Pass three experience gates

For new or substantial UI work, turn available capabilities into decisions before implementation. Small fixes keep the established direction and skip this ceremony unless they expose a broader experience failure.

1. **Select from the real task:** identify the user's primary task in the current product state, then name only the skills, methods, or platform patterns that materially help it and why. Keeping a sound framework does not require keeping an unsound interface; conversely, a newly available skill is not a reason to force its technology or visual language into the product.
2. **Make principles observable:** translate each selected principle into concrete hierarchy, state, control, content, or motion decisions and corresponding observable acceptance. Record these briefly in the existing task or project design document; do not create a new template for the sake of compliance. Keep safety, stop, and recovery actions reachable, but set their prominence from actual risk instead of hiding them or making every state equally loud.
3. **Verify the experience on its real surface:** exercise the primary task, important states and transitions, input paths, and relevant window or screen lifecycle in the target browser, app, simulator, or device. Scope coverage to the changed surface and risk. Builds, skill reads, generated code, and screenshots remain useful narrow evidence, but none alone proves that the experience is understandable or usable.

## Establish a design direction

Read the existing project instructions, working interface, and supplied references. Identify the audience, primary task, target platforms/devices, input methods, important states, brand constraints, and what will count as a successful experience.

For substantial work, communicate a short design read: what is being made, for whom, the intended experience, and the important constraints. Ask only if a missing choice would materially change the result.

Separate three decisions:

1. **User journey:** entry, actions, system feedback, completion, and actual error/empty/loading states needed by the task.
2. **Visual direction:** hierarchy, typography, color roles, spacing/density, imagery, and spatial relationships. Prefer the project's established design system when it still serves the new experience.
3. **Interaction language:** what responds to input, how state changes are communicated, and where motion or spatial behavior materially helps.

Use `refero-design` for reference research and synthesis on substantial web or product-screen design. Its styles/screens/flows are evidence sources for bounded design questions, not a requirement to research every small edit. Research native and engine-led experiences against the target platform's conventions and relevant real examples. Reference access and supplied assets must be real; do not claim live Refero research without callable tools.

Lock an actionable direction before building: primary reference or existing system, traits to preserve, required states, asset strategy, and meaningful deviations. A short explanation or an update to an existing project design document is enough. Do not create a separate document for every component change.

When no color direction is specified and no existing brand or project palette governs the surface, choose one pair from [references/color-pair-palette.md](references/color-pair-palette.md). Treat it as a candidate pool instead of inventing a generic purple-blue gradient; preserve semantic colors and measure the actual foreground/background contrast before adoption.

For a dashboard, analytics workspace, operations console, or data-heavy admin surface, read [references/dashboard-composition.md](references/dashboard-composition.md). Establish the user decisions and data semantics first, then ask where the visual weight lands, who or what receives the first screen, and what can be removed without losing meaning. Its eight examples and percentages are source observations for comparison, not universal style tokens or layout quotas.

For de-AI UI critique, generic generated-looking UI, or template-like business-dashboard polish, read [references/de-ai-ui-checklist.md](references/de-ai-ui-checklist.md). Apply its checks to the changed surface even for a small UI task; preserve the brand, accessibility, useful density, project style, and real data instead of imposing a neutral-gray preset.

For profile cards, team pages, or personal introductions, read [references/profile-card-layouts.md](references/profile-card-layouts.md) when layout direction is needed. Select by content priority; the twelve examples are alternatives, not a mandatory monochrome style.

For edge-to-edge mobile web, hybrid, or native layouts that can meet device cutouts or system chrome, read [references/safe-area-layout.md](references/safe-area-layout.md). Treat the current runtime container as the source of truth; third-party device lookups may explain a case but do not replace runtime insets or target-surface testing.

For a new or substantially revised responsive type system, read [references/responsive-typography.md](references/responsive-typography.md). Keep semantic heading structure separate from visual type roles, and derive scale, measure, spacing, and breakpoints from the actual language, font, content, accessibility needs, and container rather than copying a specimen's numeric ladder.

For popup or overlay selection—Modal, Drawer, Toast, Dropdown, Popover, or Tooltip—read [references/six-popup-types.md](references/six-popup-types.md). Choose by task, interruption, and interaction semantics; visual shape does not determine modality or keyboard behavior.

For `Liquid Glass`, `glassmorphism`, frosted glass, translucent navigation, or glass cards, read [the glass-material selection recipe](references/technology-selection.md#select-glass-materials-by-mechanism). Distinguish native platform material, CSS backdrop blur, and real refraction before choosing an implementation; keep the existing platform and let content, state, and contrast outrank the effect.

## Assign specialist work without competing directions

Specialists contribute within the user's brief and established direction. Their stack preferences, aesthetic defaults, and fixed numeric heuristics do not justify changing the project or claiming platform facts without verification.

Every named external skill, tool, service, and provider below is optional unless the user's task explicitly requires that exact capability. Discover whether it is actually available before relying on it. When it is absent, continue with this skill's included core and references plus the project's existing components, platform APIs, and toolchain. Do not claim missing research or provider-backed work, and do not silently change a required outcome, asset source, provider, format, or production dependency. Report the exact missing capability only when it is essential to complete or verify the requested result.

## Select the implementation

### Reuse component source before writing new UI

For every UI component task, including small changes, first make a targeted search of the project's component directories, this skill's `references/`, the host's available skill catalog or source assets, and relevant reusable component sources that are actually available to the task. Prefer an existing component or the smallest suitable adaptation over writing from scratch; search by the requested behavior and target framework rather than scanning every library in full.

Before adopting a candidate, inspect its actual source, license, dependencies, platform fit, and accessibility against the project. A reference, preview, or skill is not necessarily reusable component source. Preserve required notices and obtain any required dependency authorization. If no suitable source exists, or a candidate is unsuitable, briefly state the concrete reason in the existing task notes before authoring new code; no separate report is needed.

In the delivery summary, name the reused source, material adaptations, and applicable license boundary, or explain why new code was necessary. Reuse does not replace the skill's real-surface verification gate or authorize installation, migration, or publication.

When the experience needs a technology choice, read [references/technology-selection.md](references/technology-selection.md). Existing frameworks are neither disposable nor untouchable: change a layer only for a concrete capability need, explain the cost, and keep the work within the requested scope.

Choose the rendering and interaction layer from the desired experience, asset workflow, target devices, accessibility, runtime cost, and delivery constraints. A new library being installed globally as a skill does not install a runtime into the product.

Build the smallest usable slice that demonstrates the central interaction. Preserve unrelated work, product contracts, and project ownership. Resolve conflicting animation ownership rather than letting two libraries update the same property independently.

### Use community component snippets selectively

For ReactDrops, AI-ready component briefs, Showcase Pointer, Refracted Text, Fractal Glass, Liquid Glass Logo, or Liquid Glass Orb, read [references/reactdrops-component-patterns.md](references/reactdrops-component-patterns.md). Select one fitting drop, verify its source and custom license, and adapt the brief to the existing project; this does not install a component or replace the motion and glass rules.

- Inspect the project's existing components and design system first. Use [Uiverse](https://uiverse.io/) as an optional source for one small, generic web element when selective adaptation is cheaper than building it locally; do not import the catalog or let a decorative snippet define product behavior.
- The site advertises HTML/CSS, Tailwind, React, and Figma outputs, while its [Galaxy repository](https://github.com/uiverse-io/galaxy) describes CSS/Tailwind elements. Verify the chosen element and output actually exist, review all markup, styles, scripts, and dependencies, then adapt them to the project's framework and tokens. Scope generic selectors, custom properties, and keyframe names so copied CSS does not leak across the application.
- Record the exact element URL, author, and current license before copying. Preserve a `From Uiverse.io by ...` comment when practical as provenance, but do not mistake it for the complete license notice: Galaxy says attribution is appreciated rather than mandatory, while its [MIT license](https://github.com/uiverse-io/galaxy/blob/main/LICENSE) requires the copyright and permission notice in copies or substantial portions.
- Treat the snippet as an unaccepted starting point. Preserve native semantics and visible focus, support keyboard and touch input, make hover-only behavior nonessential, honor reduced motion, and inspect the actual component states at target sizes before production use.

When a user describes an effect in conversational language or asks for wording to give a designer or coding agent, read [references/motion-description-vocabulary.md](references/motion-description-vocabulary.md) before choosing an implementation. First name the trigger, motion shape, and interaction outcome; then turn that label into an explicit behavior contract. Treat compound scene labels as descriptive prompt language rather than standardized motion terms or evidence of a particular rendering technique.

For `Linear` / `HAIRLINE`, `hairline-create`, `figures`, thin isometric line art, or pointer-responsive SVG illustration requests, use the Hairline selection and implementation recipe in that reference. It distinguishes an existing project component, the verified `@lucasmarkes/hairline` asset, and a custom authored figure; commonly misreported `lucasmaystre` / `@lucasmaystre/lineicons` names are search aliases, not verified package coordinates.

### Use OpenPencil as an intentional design workspace

This guidance refers to [ZSeven-W/openpencil](https://github.com/ZSeven-W/openpencil) and `op.zseven.tech`. `openpencil.dev` currently identifies a different repository and is not evidence for this tool's capabilities.

- **Use it for an editable design handoff:** choose it when the task benefits from an agent-editable vector canvas, a reviewable/versionable `.op` artifact, `.fig` ingestion, repeated frame export, or deliberate multi-framework scaffolding. Its `.op` format is JSON-based; the implemented code generators target React, Vue, Svelte, HTML, Flutter, SwiftUI, Jetpack Compose, and React Native.
- **Do not insert a canvas by default:** keep Figma when its shared libraries, comments, prototypes, or team review are the source of truth. Work directly in the project's code when the design direction and component system already exist, the change is small, or responsive behavior, semantics, data, and runtime states are the main problem.
- **Pass a readiness gate before editing:** verify the surface that will actually be used. On the CLI path, check `op status` and `op tools`; on a direct MCP path, use its equivalent connection/ping, tool discovery, and read-only layout call instead of requiring the `op` binary. If an existing `.op` file is the target, inspect that file and its layout before writes; a new draft may start from an explicitly chosen blank document after the selected surface passes readiness. Do not assume the default port, a provider, or a currently exposed OpenPencil tool.
- **Treat Figma import as conversion, not round-trip parity:** `op import:figma` produces an `.op` file and reports warnings. Inspect warnings, fonts, images, components, auto-layout, clipping, and rendered geometry; do not claim lossless Figma compatibility or reverse export without separate proof.
- **Keep the design artifact separate from production acceptance:** generated framework output is a scaffold/handoff, not accepted application code. After an authorized change, export the affected frame or page, inspect the render, and integrate only the useful structure into the existing framework; re-verify responsiveness, semantics, accessibility, state behavior, tokens, assets, and project tests.
- **Separate local files from provider traffic:** an inspectable local `.op` file does not prove that AI prompts or assets stay on-device. Before any provider-backed generation, identify the selected provider, credential, data egress, output rights, and user authorization; deterministic canvas/CLI/MCP work does not itself authorize an external AI call.

For component motion timing or token review, read [references/component-motion-tokens.md](references/component-motion-tokens.md). Match tokens by purpose rather than nearest numeric value; keep the project's motion system and the actual state-transition contract authoritative.

## Preserve continuity in stateful motion

Treat advanced card, button, layout, and gesture motion as a state transition rather than a collection of keyframes. Before implementation, identify the source state, destination state, spatial anchor, commit/cancel conditions, and reverse path. The user should be able to answer: where did it come from, what did it become, and where did it go?

For completion bursts, linked page feedback, stacked-card fans, snap-and-draw sequences, inertial wheels, or circular page reveals, read [references/six-app-interactions.md](references/six-app-interactions.md). Reuse the stateful-motion rules and Advanced Interaction Techniques table there instead of duplicating their mechanics.

- **Anchored reveal and return:** derive the transform origin or reveal geometry from the invoking control, including its actual press point when that is meaningful. Open and close through the same relationship. Animate the shell and content separately: keep text and detailed content visually stable with a bounded inverse-scale layer or geometry animation, and reveal it after the shell has enough room. A spring may overshoot when it reinforces emergence, but the source, target, and return path matter more than bounce.
- **One control, several semantic states:** for actions such as submit, keep one control in place while it moves through idle, pressed, pending, and success states. Preserve its layout footprint, prevent duplicate activation, expose pending/success semantics, and animate the progress and completion mark inside the same object. Do not use a navigation or modal to imitate a control transformation.
- **Gesture settlement:** combine displacement and release velocity when deciding a carousel, page, or card destination. A deliberate drag past the threshold advances predictably; a fast fling may advance farther when the content model permits it. Neighboring items should preview distance and destination through restrained scale/opacity/depth. Test slow drags, fast flings, reversal before release, bounds, and interruption.
- **Shared-identity layout changes:** keep stable item identity when switching list/grid or other layouts. Interpolate each item's measured position, size, and shape with a shared-layout or FLIP-style technique; animate internal layers separately where needed. Do not reload the surface or crossfade two complete layouts through an overlapping ghost frame.
- **Staged collection changes:** sequence filtering as `OUT -> MOVE -> IN`. Exiting items fade/scale at their current positions, survivors then move into resolved slots, and entrants appear from their assigned slots. These phases must remain perceptually distinct so users can tell what left, what stayed, and what arrived.
- **Depth follows input:** for press/drag card tilt, tie perspective, highlight direction, and layered parallax to the same input. Foreground artwork may move slightly more than the card plane to imply thickness; keep the difference subtle, bounded, and reversible. Touch must not depend on hover, and reduced-motion behavior must remain understandable.
- **Interruptible long press:** use the target platform's recognizer or roughly 400 ms as an initial product-UI threshold, then verify accidental activation and responsiveness on the target device. After lift, maintain explicit return, commit, and cancel outcomes; allow direction changes before release, show the active destination, resolve gesture conflicts, and provide an accessible non-gesture path for the same action.
- **Mode transitions are coordinated:** entering multi-select or another page mode updates the whole relevant surface from one state source: item affordances, spacing, selection count, navigation/title, and action bar. Exit restores the previous mode coherently. A local checkbox appearing without the surrounding mode change is incomplete.

For reduced motion, preserve state causality and final geometry with a shorter, simpler transition or direct state change; do not remove feedback about pending, success, selection, commit, or cancel.

## Advanced Interaction Techniques

Use this parameter table when a request names or needs one of these ten demonstrated client-interaction techniques. Each is a state-transition reference, not a decorative-animation catalog. For drag, selection, and release-settlement interactions, the surface follows input, a named threshold decides commit or cancel, and the result settles onto a defined target. STROKE, click-triggered fly-ins, and page transitions instead complete according to their actual trigger and terminal state. The values below are demonstrated reference values, not universal platform constants. Apply them inside the design direction and the stateful-motion rules above; route conversational or scene-label descriptions through [references/motion-description-vocabulary.md](references/motion-description-vocabulary.md), choose the lightest layer through [technology selection](references/technology-selection.md#select-advanced-interaction-techniques), and when document scroll is the driver, keep the property mapping in the scroll chapters below (Build scroll-driven motion as a narrative system, Build scroll-driven video).

| # | Technique | Key parameters |
| --- | --- | --- |
| 01 | **FAN (card fan)** | Put the transform origin outside the card: `transform-origin: 50% 150%`. One rotation per card around that shared external pivot produces the whole spread and arc, not four unrelated trajectories. Collapsed and expanded states share one layout. |
| 02 | **INERTIA (wheel picker)** | Reference: after release, decay `v *= .93`; only when `|v| < .42` begin snapping with `y += (nearest - y) * .2`. Treat `v` as per-60-Hz-reference-frame and apply both against elapsed time: decay `.93 ** (dt / (1000 / 60))`, snap `1 - (1 - .2) ** (dt / (1000 / 60))`, rather than once per `requestAnimationFrame` callback. Inertia and snap stay strictly ordered. |
| 03 | **SHEET (half-screen sheet)** | On release, close when `displacement > 1/3` **or** `velocity > .55 px/ms`—either condition alone. Do not judge from drag distance only: a 26% displacement with a `.71 px/ms` fling still closes. |
| 04 | **PARABOLA (parabolic fly-in)** | Reference timing: X `linear`, Y `ease-out`. Independent X/Y progress (for example, nested layers) can compose this arc; a defined motion path/path animation is another valid route for a geometric curve. Do not treat one transform as universally incapable of curved movement. |
| 05 | **COLLAPSE (large-title collapse)** | One scroll progress drives scale, horizontal shift, vertical shift, and background together. Derive the horizontal shift from measured width as `(W - W * S) / 2` rather than hard-coded pixels, so a font or column change does not break alignment. |
| 06 | **REORDER (long-press drag reorder)** | Reference: start after a `260ms` long press; cancel if movement is `>8px` first. During drag, use a slot array plus `transform`, keep DOM/focus order stable, and let the dragged item follow with transitions off while the rest yield. After a committed reorder, update the logical/reading order (including DOM or equivalent semantics where needed); provide a keyboard path for the same operation. |
| 07 | **FLIP (shared-element zoom)** | Measure the First and Last rects, pin the expanded element onto the thumbnail's rect with `transition: none`, then release it after the target runtime has committed that starting state; `.42s` is the reference duration. One `requestAnimationFrame` often works in direct DOM, but is not a cross-runtime guarantee—verify the inverted state before release. |
| 08 | **STROKE (handwriting stroke)** | Use `getCoalescedEvents` on targets that expose it, smooth through midpoints with quadratic Béziers, and define the speed unit before using the reference response `w = 5.4 - speed * 7`. Clamp width to a positive `[wMin, wMax]` range so fast input cannot produce an invalid width. |
| 09 | **STICKY (sticky drag)** | The stickiness is in the anchor, not the band: shrink it as `r0 = R * (1 - d / 66 * .72)` and break the link past `66px`. Thin the band while the anchor stays put, or it reads as taped on. |
| 10 | **Page transition** | The original observation did not include visual frames. Treat old-page recession/dimming coordinated with the incoming page as an unverified direction; holding the old page still makes the incoming page read as an unwanted sticker. Then define actual source/destination geometry, focus transfer, and interruption behavior on the target surface. |

Use follow, threshold, and snap as the review filter only for drag, selection, and release-settlement interactions. For STROKE, click-triggered fly-ins, and page transitions, verify the actual trigger, feedback/path, and terminal state instead. Give each animated property one owner, preserve reversed and interrupted paths, and keep the reduced-motion state understandable. Gesture-only actions need an equivalent keyboard/non-gesture route; focus, reading order, and announced state must agree with the committed result.

## Design playable, shareable micro-sites

Use this when the goal is one small, self-contained participatory site rather than a product surface: the interaction itself is the hook, and the visitor's own input can become the object that competes. A representative loop combines a bounded creation challenge, one lightweight audience action with visible progress, and a result or leaderboard. Treat that as a play-loop pattern, not evidence that any particular model or feature causes engagement or sharing.

- **Participation before polish:** The observed loop makes a visitor-drawn horse the entrant, then exposes race progress and rank. Keep one loop, one input, and one visible result; a personal artifact and comparison can be a shareable hook when they serve the actual product goal, but do not claim they create distribution without product evidence. Avoid navigation, accounts, or a tutorial before the loop unless the real goal requires them.
- **Hand-drawn restraint:** The sample uses a pale paper-like field, a few basic colors, and deliberately imperfect lines, reading as playful rather than unfinished. Use that looseness as a deliberate visual choice, not a universal viral style or an excuse to omit legibility and controls; do not wrap this small loop in an unrelated polished product system.
- **Deadpan copy carries the tone:** The sampled labels—“The questionable derby”, “Barely a horse”, “Horse.exe”, and “Unstable”—set expectation and carry the joke with restrained text. Let plain wording and tone do that work rather than decorative effects, without treating those phrases as a proven engagement mechanism.
- **Instant, low-ceremony feedback:** The sample shows a cheer action, progress, and rank. Make one action lead promptly to a visible result; do not promise a real-time leaderboard unless the data contract supports it, and do not add loading ceremony, settings, or tutorial gates before the core loop without a product need.

Use the stateful-motion rules above for this loop rather than inventing a second interaction model. Apply follow/threshold/snap only when a drag, selection, or release-settlement interaction actually needs them; otherwise complete each action through its actual trigger and result. A pointer-drawing hook needs an equivalent keyboard/non-pointer way to create or select an entrant, and entrant, progress, rank, and result need text-readable status. Verify the actual changed surface: entry, repeated rounds, touch and keyboard paths, interruption, and reduced motion.

## Build playable Three.js browser games

Use this when the requested experience is a game rather than a 3D scene or viewer. [Three.js Game Skills](https://github.com/majidmanzarpour/threejs-game-skills) is a workflow reference for this section, not an installed runtime, a requirement to install its nine-skill pack, or evidence that any bundled test has run. Its reusable packaging lesson is one director contract routing narrow specialists: each `SKILL.md` owns the entry contract, references load on demand, and scripts/assets carry executable templates. Load only the capability the task needs and verify its outputs; this structure does not require separate agents or broad installation.

- **Write the play contract first:** name the player verb, objective, progress signal, fail/complete conditions, retry path, camera, inputs, target devices, and representative encounter. A rendered scene, orbit camera, or title screen is not a playable loop.
- **Prove the smallest complete loop:** implement one representative slice from input through world response, objective progress, fail/complete, and retry before multiplying levels, enemies, effects, or generated assets. Judge visual direction in active play at the real camera scale, not from an isolated hero render.
- **Keep simulation observable and reproducible:** give runtime systems explicit ownership, route gameplay randomness through a seeded source when repeatable QA matters, and expose test hooks/diagnostics only in the approved test surface. Hooks must acknowledge the requested state; they set up evidence but do not replace exercising real controls.
- **Separate behavioral and visual proof:** run the production build and a real browser, check console/page/network failures, drive the main controls through progress and retry, capture active play at supported viewports, and inspect performance and animation when affected. Nonblank canvas pixels prove rendering only. A scripted bot proves only the adapted assertions it actually drove; the upstream `bot-playtest.template.ts` is a game-specific template, not autonomous universal testing.
- **Choose and ledger assets deliberately:** record source, license/usage terms, version or provider task ID, local path, transforms/compression, and runtime budget for third-party or generated models, images, textures, and audio. Core Three.js gameplay needs no paid model key; Tripo, Gemini, and ElevenLabs are optional external generation routes requiring explicit authorization, configured credentials, and current output-rights review. Missing credentials do not authorize a silent asset-quality or provider change.
- **Use the right 3D route:** `img2threejs` owns reference-image-to-editable procedural Three.js reconstruction with its fidelity gates. Provider-generated GLB/FBX is an optional asset-sourcing route and must be inspected in the game for scale, pivots, topology, materials, animation/rig behavior, loading cost, and license. A downloaded or image-to-mesh asset is not animation-ready, performant, or visually accepted by default.

Claim completion only from current-run evidence tied to the current build. Screenshot baselines, canvas metrics, manifests, skeleton checks, and model downloads each prove a narrow property; none alone proves gameplay quality, visual quality, mobile behavior, or release readiness.

## Design input-state microinteractions

Treat OTP, verification-code, PIN, and other segmented-input motion as feedback around a real form control, not as a replacement for input semantics. Keep one source of truth for the value and status. On the web, use text input semantics so leading zeroes survive, add an explicit label, set `inputmode="numeric"`, and put `autocomplete="one-time-code"` on the input that owns the code so operating-system autofill remains available.

- **Build one hand, not several tilted boxes:** for a card-fan reveal, align the slots around one shared visual pivot below the cards. `transform-origin: 50% 320%` is the reference geometry; one per-card rotation around that pivot should create both the spread and the arc. Use measured translation only to align that geometry, not to fake four unrelated trajectories.
- **Use stagger as one transition:** start with the demonstrated `560ms` duration and `45ms` per-slot stagger, then tune to the product motion system and target device. Give the card transform one animation owner. Cancel or retarget outstanding animations when autofill, paste, correction, or a new state supersedes them, and leave DOM and focus order logical rather than matching the visual fan.
- **Make acceptance travel around the edge:** an SVG `rect` with `pathLength="1"` plus dash animation can run one lap around the accepted slot. Treat it as decorative, keep it out of the accessibility tree, and do not loop it or use glow as the only evidence that a digit was accepted. Animate only slots whose value actually changed, including distributed paste.
- **Preserve editing behavior:** accept the allowed code format at the input boundary, distribute a pasted code left-to-right from the replacement position, and never disable paste. Support replacement, selection, Backspace, arrow-key navigation, and mobile keyboards without moving focus to match the visual arrangement. Enter submits the actual form only when the required code is complete; incomplete submission should expose guidance rather than silently doing nothing.
- **The wait is not a verdict:** pending verification is neutral, not success or failure. Retain the entered code, prevent duplicate submission, set the owning region's busy state, and announce one concise status through the platform accessibility API. Move to accepted or rejected styling only after the authoritative result; keep resend and its real cooldown as a separate action.
- **Keep the reduced-motion and error paths complete:** reduced motion may show the final grouping directly or use a short opacity/outline change, but it must retain focus, accepted-digit, pending, error, resend, and completion feedback. Associate errors with the field, keep visible focus and adequate targets, and never encode status through tilt, color, glow, or animation alone.

## Build scroll-driven motion as a narrative system

Use scroll motion when it reveals structure, explains change, or advances a deliberate story—not merely because the page is long. For a substantial scroll-driven site, pointer-following character, product sequence, or generated-media timeline, read `oil-motion` and use its production workflow after the design direction is set. For large-title collapse, or another interaction with the same measured geometry, take the width-derived `(W - W * S) / 2` formula from 05 COLLAPSE rather than re-deriving it; do not impose it on unrelated scroll effects.

- **Storyboard before code:** define stable visual states and the one meaningful change between each pair. Record what must remain invariant—identity, product geometry, logo, camera anchor, lighting, background, or typography—and make every important stopping position readable as a still frame.
- **Scroll is an input, not automatically one global timeline:** choose continuous `scrub` when position must map directly to progress, or `segment-play` when crossing a threshold selects a transition that then completes. Keep page navigation, sticky-section progress, and media time as separate concepts; map the smallest relevant scroll range rather than stretching the entire document over one asset.
- **Segment the timeline:** normalize local progress, assign ordered ranges to story beats, and give each segment explicit start, hold, and destination states. Preserve forward and reverse continuity from the current frame. Compile timing from the final asset or implementation instead of duplicating hand-written seconds across page code.
- **Pointer following needs a physical model:** decide whether the input controls limited yaw, a front-facing gaze orbit, turntable rotation, or a genuine two-dimensional pose space. Measure the pointer relative to the subject, update only the target in the input handler, and perform smoothing/rendering in one animation loop. A touch or non-pointer experience must preserve the intended information without pretending to provide cursor tracking.
- **Bind camera and material changes to the same progress source:** use deterministic transforms, Three.js cameras/materials, or shaders for geometry, lighting, reveal, and viewpoint changes that can be expressed programmatically. Give each property one owner and keep DOM content outside baked media. Use generated frames/video only when semantic deformation, contact, occlusion, or material evolution cannot be preserved by moving existing layers.
- **Lock media ownership and aspect ratio early:** decide whether the scene background belongs inside the generated media or to the page, and derive source aspect ratio and pixel dimensions from the real desktop/mobile container and DPR. Do not generate a square master for a full-screen landscape or portrait stage and repair it with destructive cropping later.
- **Pilot before volume:** prove one keyframe pair or one segment in its real page position before producing the rest. Verify reverse input, rapid changes, intermediate stills, cold loading, target viewports, reduced motion, and frame-time/media budgets; repair failed identity or continuity upstream instead of hiding it with runtime effects.

## Build scroll-driven video

Treat scroll-driven video as a specialized delivery and time-control route inside the scroll narrative above: a linear, pre-rendered video owns the camera, lighting, material, contact, and semantic transformation, while scroll only selects its playhead position. Use it when those changes are better baked than reconstructed from page layers. Keep text, controls, and deterministic layout or geometry in DOM/CSS/SVG/Three.js when they need to stay accessible, responsive, or independently interactive. For generated or multi-clip production, use `oil-motion`; for an existing approved video, begin at media analysis, encoding, and runtime mapping. Page-level gesture, layout, or transition techniques that run alongside the video come from the Advanced Interaction Techniques table above and keep their own properties, never the seek timeline.

- **Lock the journey before the controller:** turn the brand, product, or theme into ordered, readable scene states, then produce one continuous journey for each required aspect ratio. Runtime scroll code cannot repair a subject, camera, light, or environment that drifts between scenes.
- **Lock seams with rendered boundary frames:** use the previous clip's actual decoded tail frame as the next clip's input and compare the encoded tail/head pair after every trim, interpolation, or transcode. Compile an approved chain into one persistent video per device class; do not swap `src`, crossfade clips, or hide a broken seam at runtime.
- **Encode for seeking, not ordinary playback alone:** prefer a broadly supported H.264 MP4 with the index moved to the front (`+faststart`), a known constant frame rate, no unused audio track, and native desktop/mobile dimensions. Continuous random-access scrub needs dense keyframes; the `oil-motion` frame-scrub route uses all-keyframe output. If another pipeline uses a longer GOP, set and verify a seek-latency budget on target devices rather than assuming visual bitrate quality proves responsive seeking.
- **Make loading-to-video a frame-accurate handoff:** derive the poster from the final encoded first frame with the same crop and sizing. Wait for metadata before seeking, keep the poster visible until the first requested video frame is decoded and painted, then crossfade without changing layout. `preload` is a browser hint, not readiness proof; bind readiness and errors to observed media state.
- **Map scroll to the compiled timeline:** normalize the local stage range as `p = clamp((scroll - start) / (end - start), 0, 1)` and map it to `0 .. duration - frameDuration`. The source recipe's `duration - 0.04` is a one-frame guard for 25 fps, not a universal constant. Scrolling up and down must seek both directions, and stopping must hold the corresponding frame.
- **Schedule seeks through one owner:** scroll or ScrollTrigger callbacks update only the latest target. One `requestAnimationFrame` loop clamps it, ignores sub-frame churn, and submits at most the newest useful seek instead of queueing stale `currentTime` writes. Use the final encoded frame rate and timeline as the source of truth; do not duplicate scene seconds in components.
- **Choose exact or trailing scrub deliberately:** direct mapping or `scrub: true` keeps the playhead attached to scroll. A numeric ScrollTrigger scrub or a lerp intentionally continues catching up after input stops. Use at most one smoothing owner, state that behavior in the motion contract, and do not stack ScrollTrigger smoothing with a second video-time lerp.
- **Design the mobile and iOS policy:** a true scrub video stays paused and uses one persistent `<video muted playsinline>` without controls, autoplay, or loop. Autoplay belongs to autonomous playback; loop only belongs to a continuity-tested closed journey. Choose an explicit user-start gesture when actual playback or audio requires it, handle a rejected `play()` promise, ship a smaller native mobile source, and avoid eagerly loading both device versions. Use `preload="auto"` only when the primary experience and data budget justify it; otherwise define when metadata or the chosen source begins loading.
- **Keep page motion separate and inclusive:** pointer parallax may move the visual container by a restrained amount such as `±30px`, but must not alter video time; remove it for touch and the planned reduced-motion state. DOM text may scrub reversibly through position, stretch, and opacity on named ranges—the source's `yPercent: 250` and `scaleY: 1.2` are examples, not defaults—and must remain legible, selectable, and correctly ordered. `prefers-reduced-motion` selects the explicitly designed static or discrete story state; it is not an error-time media fallback.

External image or video generation is a separate authorized operation. When the task requires newly generated assets but lacks a configured credential or permission for the selected provider, stop at the concept contract, scroll storyboard, keyframe/prompt plan, asset manifest, and frontend code skeleton. Do not probe for, expose, or reuse unrelated credentials. User-supplied video or frame sequences may proceed through validation, Pilot, delivery budgeting, media compilation, and runtime integration without a generation credential.

Interpret loading composition and reduced motion as explicit planned product states, not runtime fallbacks. Do not adopt an alternate provider, media format, or static substitute automatically when generation, decoding, or resource loading fails; surface the failure and release any page lock. Change the delivery route only when the user or project requirements authorize it.

## Design loading as system feedback

Treat loading as a real product state, not a decorative intermission. Use determinate progress when completion is measurable, a structure-matched skeleton when content shape is known, and a compact indeterminate indicator for a short wait whose progress cannot be measured. Bind it to the actual pending state, reserve its footprint to avoid layout shifts, and keep longer or consequential waits understandable with plain status text.

For a bespoke circular indeterminate indicator, a self-contained animated SVG is a strong default when it fits the established visual language: one selected asset can carry markup, keyframes, and color without adding JavaScript or a runtime dependency. Provide intentional light/dark ink and surface colors, adjustable size and tempo, and a composed still state under `prefers-reduced-motion`; reduced motion must not produce a blank indicator. Use [Circle Loaders](https://circleloaders.dominikakissi.com/) as an optional CC0 reference library, not as a mandatory dependency or a reason to import all 24 variants.

Keep the visual animation separate from status semantics. Mark a decorative SVG hidden from assistive technology when nearby text communicates the state; expose the owning region's busy state and a concise status through the target platform's accessible APIs. Inline SVG is appropriate when the host must control theme, semantics, or motion; an `<img>`, CSS background, or `<object>` is appropriate for an isolated file, with explicit theme variants because the host cannot freely style an external SVG's internals.

For geometric SVG construction such as phased wedges, projected rings, or seamless periodic paths, read the loading-indicator section in [references/technology-selection.md](references/technology-selection.md). Copy only the chosen asset, preserve its license/provenance where the project records third-party material, and inspect the real light, dark, normal-motion, and reduced-motion result. Zero JavaScript does not by itself prove low rendering cost when many instances, filters, masks, or dense geometry are present.

## Verify the delivered experience

Verification follows the changed surface, not a universal checklist of platforms:

- Inspect real rendering at relevant web viewports or native/device/simulator targets. Exercise the primary interaction and changed states, including repeated input where motion can be interrupted.
- For continuity-driven motion, verify the source and destination geometry, forward and reverse paths, threshold/velocity outcomes, mid-gesture reversal, cancellation, rapid repetition, and mode exit. Reject layout jumps, stretched text, double-rendered layouts, ambiguous filtering phases, and controls that move unexpectedly.
- For OTP or segmented inputs, verify digit-by-digit entry, full-code paste, operating-system autofill where available, replacement, Backspace, arrow keys, incomplete and complete Enter submission, rapid correction during motion, pending, authoritative success/error, resend, and reduced motion. Confirm that visual order never changes DOM, focus, or announced status order.
- For scroll-driven motion, verify local progress boundaries, stable segment holds, forward/reverse continuity from the current frame, programmatic-navigation isolation, pointer/touch behavior, media readiness, and the intended reduced-motion state at real desktop and mobile dimensions.
- For scroll-driven video, verify poster-to-first-frame continuity, cold and constrained-network readiness, exact stage endpoints, slow/fast seeks, large jumps, rapid reversals, stop-to-hold behavior, keyframe seek latency, background-tab recovery, mobile source selection, and the planned reduced-motion state. Inspect actual decoded seam frames and reject white flashes, stale seeks, duplicated media layers, crop changes, and motion that keeps advancing after an exact-scrub stop.
- Check keyboard/focus, labels, touch behavior, contrast, and reduced-motion behavior where applicable. Use `fixing-accessibility` for matching web controls/forms and platform-native checks for native UI.
- For changed loading states, verify that the indicator starts and settles with the real operation, the surrounding layout does not jump, visible and accessible status agree, light/dark variants remain legible, and reduced motion shows a meaningful still state. Test repeated instances when SVG filters, masks, or dense geometry could affect frame time.
- For Three.js games, verify the active loop with real input: objective progress, fail/complete and retry, current desktop/mobile targets, console/page/network health, canvas/render evidence, and affected animation/performance. If a bot template is adapted, report its seed, input script, assertions, metrics, and limits rather than calling it general playtesting.
- Use `fixing-motion-performance` when animation changes need that check; measure the actual interaction when performance is a selection gate. Use `fixing-metadata` for affected public/shareable web pages, not every client screen.
- Run the smallest project type/build/test check covering the change. Distinguish static validation, rendered observation, simulator evidence, real-device evidence, and deployment.
- Report missing assets, device/tool access, or failed acceptance directly. Installed skills, a connected CLI/MCP, and generated code do not prove a finished experience.
